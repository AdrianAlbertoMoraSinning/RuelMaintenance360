# Dispatch map, customer link and departure · 0.3.9

Set / edit coordinates opens an interactive OpenStreetMap / Leaflet map. Click or tap the actual delivery point, verify latitude/longitude and the green radius (75–1000 m), then Save coordinates. Panning and zooming never save a location by themselves. Google Maps can be opened separately to find an area; paste its coordinate pair or a full URL with coordinates to center the integrated picker. Short sharing URLs are not resolved. Manual entry and on-site GPS remain available if map tiles fail. Standard OSM attribution and browser tile caching are retained; no bulk/offline tile downloads or geocoder requests are made. Maps require connectivity. Saved coordinates use the existing geofence API. Already-ready loads retain their zone snapshot until Update delivery zones is explicitly used before departure.

The order detail ends with Customer tracking link and Copy tracking link. Valid links created after this update can be retrieved by an authorized order manager without rotation; read requests never create a token. Tokens are retained only in the private tracking table and returned by an actor-bound manager API. They are not included in workspaces, public tables or activity payloads. Existing hash-only links keep working and are never replaced automatically; the user must explicitly confirm replacement if they need a newly recoverable link. Replacement invalidates the old link, has an idempotency key, and keeps the 90-day lifetime. Copying does not email or SMS the customer.

Dispatch sequence: Plan delivery (driver + active vehicle + quantity) → Confirm produced & ready → Mark departed. A manager must confirm the actual physical departure, which records their identity, timestamp and dispatcher source. This is the same departure milestone the driver or foreground geofence can report. The assigned driver can acknowledge an already-recorded dispatcher departure without duplicating it. The order creator receives an in-app notification, and the customer’s tracking updates. A driver/vehicle with an active trip cannot be dispatched again. Departing never accepts the delivery or creates a customer signature.

Orders show confirmed, partially dispatched or dispatched according to actual departed quantities; the underlying open-order state remains compatible with remaining-load assignment, receipts and completion. The public tracking derives the same status. No planned time is treated as an actual event.

Network handling retries reads once and retries writes only when they carry server-supported request identifiers. Permission/validation errors are not retried. Background refresh failures show reconnect guidance while preserving forms and the previous workspace. A committed command is returned as successful even if the following refresh fails; this prevents a successful save being presented as a failed write. The reported browser message alone cannot prove the network failure’s originating cause.

Validation: component/model tests cover map click selection, coordinates, safe retries, tracking UI and dispatch display. Transactional SQL tests verify reusable/legacy/replaced links, authorization, real departure, single-event retries, creator notification, occupied driver checks, customer tracking, driver acknowledgment and no invented acceptance. Existing logistics, geofence, customer receipt and order chat SQL tests remain passing. QA transactions are rolled back.

# Supervisor email → manual forwarding → operator username

Mobile numbers are contact details only in profiles and the personnel roster. The system never sends an SMS. Phone Auth stays disabled. Each operator signs in with an immutable account username (op- followed by twelve UUID hex characters) and their own password; the activation page and supervisor email display that username. Supabase Auth uses an internal .invalid address solely as the username credential, never as a contact address or email destination. Profile email remains null unless the employee supplies a real contact email. Password recovery for these users must be handled through an administrator, not sent to the internal address.

The assigned supervisor receives the operator’s personal link by email and copies it into a message from their own phone. The recipient sets their password, which binds the internal username identity, removes legacy Auth phone identity, and signs in through the existing email/password Auth mechanism. The real phone remains in the trusted profile for the supervisor. Neither the operator nor the supervisor verifies an SMS code. The supervisor must not set the operator’s password.

The link is a 256-bit random bearer credential in a URL fragment. Only its SHA-256 hash is stored in a private RLS-protected table; browser history is cleared before the Auth client initializes and the page uses no-referrer. It expires after 72 hours. Inspection does not consume it, so email scanners and previews cannot activate it. A valid password submission atomically claims it. A concurrent or repeated claim fails. Auth update failures release the claim; a failure after password update keeps it claimed for administrator review. Completion consumes the link, activates the retained onboarding record and writes an audit event. Clients cannot directly invoke the backend-only database functions.

The administrator prepares an expiring link for the supervisor email. Preparing a replacement revokes older pending links. Never publish activation tokens in logs, screenshots, source or shared reports. Operators enter Observations and can read only their own report history. Sending through the application uses the existing outbound email service when configured; otherwise it clearly reports that sending is unavailable and the administrator must distribute the prepared supervisor email through their connected mailbox.

Supervisor invitation routing (2026-10-21): every application-generated operator invitation is addressed to the operator’s assigned supervisor, with CC to that supervisor’s current active reporting manager. Resolve both profiles server-side for each request; never accept recipient overrides from the browser. Missing/inactive managers or invalid email addresses block preparation/sending before a token is issued. The prepared invitation panel also shows the manager CC for mailbox-based distribution. Existing invitations are not reissued by this change.

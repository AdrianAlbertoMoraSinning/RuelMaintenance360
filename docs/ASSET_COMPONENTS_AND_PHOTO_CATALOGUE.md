# Asset components, maintenance materials and photo catalogue

An asset is the maintainable machine. Its profile now contains installed components and compatible spare references drawn from the existing shared part master. Each reference can serve many assets. Relationships carry installed quantity, system, position within the machine, preferred reference and notes. Installed quantities do not move or consume warehouse inventory. After asset creation the profile opens so the component list can be entered immediately.

Asset availability shows the unit's on-hand, reserved, available and on-order quantities and storage positions. The PM configuration panel lets the planner select only the relevant asset parts, confirm service quantities and choose a fulfillment position. The batch RPC validates unit editing permission, positive finite quantities, asset compatibility, same-unit stock positions and duplicates transactionally. Existing manual catalogue selection remains available. Plan readiness uses the preferred position or the best-stocked position to match the WO generation engine; incoming stock is separate until receipt. A WO still inherits only its plan's selected materials and uses the existing reservation, purchasing and execution approval workflow.

Parts support multiple private reference photos at creation and from the catalogue or asset profile. Client uploads validate JPEG/PNG/WebP inputs and resize/re-encode to JPEG before storage. Metadata grants and Storage policies align with existing catalogue editing roles; anonymous access is denied. Reference photographs have short-lived signed display URLs. The separate query photograph is held in the client request only and is not added to the catalogue.

Photo comparison now runs on the RUEL Netlify server in `part-photo-match-local`, using bundled OpenCV (`@techstark/opencv-js` 5.0.0-release.1, Apache-2.0) and Sharp (0.35.5, Apache-2.0; libvips and its dependency notices are retained in the packaged dependencies). The libraries and their native/WASM runtime are installed at build time and shipped with the server function. No external AI service, model weights, AI API key, runtime CDN download or machine-learning inference is used for this function. The Technical Assistant is separate and its existing AI behavior is unchanged.

The server validates the signed-in account with Supabase Auth, checks active status and reads catalogue/stock through that caller's existing RLS. It accepts an image data payload, never a user-supplied URL or reference list. Reference bytes are read only from the private RUEL Storage bucket. ORB extracts local visual features and compares Hamming-distance descriptor matches; RANSAC geometric verification, a minimum inlier count and spatial coverage reject unsupported matches. A part can still be visually indistinguishable from another part. Results are candidates, never identity/fit certification, and do not claim OCR or measured dimensions. Take clear, close photos with the part filling the frame and use several reference views, including stamped markings. Code and dimension confirmation remains necessary.

Reference descriptors are kept in a bounded per-user server-memory cache, never query photographs; cold instances rebuild them from authorized photos. The server compares all images in the selected scope up to 120 photos and 999 active parts; larger scopes require a machine or keyword filter instead of silently skipping records. Images are decoded with a 25-megapixel input bound and normalized to an 800-pixel maximum side. A bounded processing deadline requires narrower searches rather than returning incomplete results. Distinct candidate parts are ranked locally, and at most five are returned with private short-lived preview URLs and authorized stock positions. No warehouse movement, installation, purchasing or AI-memory acceptance occurs.

A public GET health endpoint exposes only engine readiness and library metadata, with no catalogue data; all POST catalogue/status/comparison operations require authentication. The legacy Supabase Edge Function forwards to this same local engine for older clients, with no AI fallback. The application displays the local engine status and an explicit empty-reference warning instead of an API-key configuration prompt.

Validation: transactional database test creates two temporary machines and shared parts, verifies machine-vs-stock separation, selected PM subset, duplicate rejection, WO material inheritance and one-unit shortage, without consuming stock. All fixtures roll back. Local tests cover fulfillment position calculations, incoming separation, unsafe image input, invented match IDs, bounded full-scope batching, distinct candidates and explicit no-match/oversized-scope results. Real identification quality still depends on actual catalogue photographs and model configuration.


Photo identification results now also load each candidate part's registered machine associations through the signed-in client's existing RLS. The result shows asset code/name, business unit, installed vs compatible relationship, quantity installed where applicable, component system and installation position. These facts come only from stored asset records; the AI never infers machine compatibility from appearance. A selected machine narrows the photo comparison scope, while the resulting part lists all its machine associations visible to that user. Reads are paginated and ID lists batched; unavailable associations are reported separately without discarding the visual candidates or repeating the AI call on retry. No stock movement or purchase is performed.

Machine-association checks: `tests/partMachineLookup.test.mjs` and transactional `tests/part_machine_visibility.sql` cover a shared bearing on multiple machines, installation/compatibility labels, pagination beyond 500 links, hidden machines, no cost reads, failed lookup vs empty result and no stock changes. The live catalogue contained zero reference photos and zero machine links at implementation time, so real-photo recognition acceptance must follow the upload of genuine reference photos and asset associations. The local engine is deployed with the application and exposes a non-sensitive readiness check.


Local-engine validation: `tests/localPhotoEngine.test.mjs` compares a rotated/re-encoded synthetic reference while global network access is blocked, rejects blank and unrelated geometry, and verifies no external AI mode. `tests/localPhotoHandler.test.mjs` exercises authenticated status, catalogue-sourced IDs, private reference downloads, stock results, no-match/empty catalogue, unauthorized access and rejection of remote query URLs. These tests validate mechanics, not field identification accuracy. A real bearing acceptance test remains pending genuine catalogue photographs and machine links.

# Asset components, maintenance materials and photo catalogue

An asset is the maintainable machine. Its profile now contains installed components and compatible spare references drawn from the existing shared part master. Each reference can serve many assets. Relationships carry installed quantity, system, position within the machine, preferred reference and notes. Installed quantities do not move or consume warehouse inventory. After asset creation the profile opens so the component list can be entered immediately.

Asset availability shows the unit's on-hand, reserved, available and on-order quantities and storage positions. The PM configuration panel lets the planner select only the relevant asset parts, confirm service quantities and choose a fulfillment position. The batch RPC validates unit editing permission, positive finite quantities, asset compatibility, same-unit stock positions and duplicates transactionally. Existing manual catalogue selection remains available. Plan readiness uses the preferred position or the best-stocked position to match the WO generation engine; incoming stock is separate until receipt. A WO still inherits only its plan's selected materials and uses the existing reservation, purchasing and execution approval workflow.

Parts support multiple private reference photos at creation and from the catalogue or asset profile. Client uploads validate JPEG/PNG/WebP inputs and resize/re-encode to JPEG before storage. Metadata grants and Storage policies align with existing catalogue editing roles; anonymous access is denied. Reference photographs have short-lived signed display URLs. The separate query photograph is held in the client request only and is not added to the catalogue.

The photo identification Edge Function authenticates the caller, loads active catalogue references through their permissions, optionally restricts references to a visible asset, signs those private images and compares the query against all photographs in the selected scope. It uses the existing OPENAI_API_KEY with OPENAI_VISION_MODEL or the existing OPENAI_MODEL. A vision-capable model must be configured. It does not invent matches when the provider is absent, the library is empty or comparison fails. Scope limits require the user to narrow by asset or keyword instead of silently skipping photographs. At most 120 reference photos are compared per request in batches of eight; distinct best candidates are reranked and at most five are shown. More than 1,000 matching catalogue records requires a narrower scope. The UI shows the number of images compared.

Candidate IDs are allowlisted to the authorized photo records; invented IDs and invalid similarity values are rejected. Qualitative similarity is not a probability. Suggestions show the reference photo, part number, reason, visible markings and authorized stock availability. The user opens the reference and confirms exact part number, connections, dimensions and compatibility; identification itself never purchases, installs, issues stock or creates an accepted maintenance observation. AI requests use store:false and send only the query image and authorized reference photos/labels to the configured provider.

Validation: transactional database test creates two temporary machines and shared parts, verifies machine-vs-stock separation, selected PM subset, duplicate rejection, WO material inheritance and one-unit shortage, without consuming stock. All fixtures roll back. Local tests cover fulfillment position calculations, incoming separation, unsafe image input, invented match IDs, bounded full-scope batching, distinct candidates and explicit no-match/oversized-scope results. Real identification quality still depends on actual catalogue photographs and model configuration.


Photo identification results now also load each candidate part's registered machine associations through the signed-in client's existing RLS. The result shows asset code/name, business unit, installed vs compatible relationship, quantity installed where applicable, component system and installation position. These facts come only from stored asset records; the AI never infers machine compatibility from appearance. A selected machine narrows the photo comparison scope, while the resulting part lists all its machine associations visible to that user. Reads are paginated and ID lists batched; unavailable associations are reported separately without discarding the visual candidates or repeating the AI call on retry. No stock movement or purchase is performed.

Additional checks: `tests/partMachineLookup.test.mjs` and transactional `tests/part_machine_visibility.sql` cover a shared bearing on multiple machines, installation/compatibility labels, pagination beyond 500 links, hidden machines, no cost reads, failed lookup vs empty result and no stock changes. The live catalogue contained zero reference photos and zero machine links at implementation time, so real-photo recognition acceptance must follow the upload of genuine reference photos and asset associations. The matching Edge Function is deployed; provider availability is checked by the existing authenticated status request.

# Dispatch logistics · 0.3.7

## Create a concrete order
Enter the customer, jobsite, mix/product, order quantity and required first arrival at the jobsite (Alberta time). Under Dispatch logistics, enter the available truck count. This is separate from the number of loads/trips: a truck can return for another trip.

Generate the distribution using the number of trips, first departure from the plant and departure interval. An optional quantity per full load produces a smaller final load; for example 20 m³, three trips and 7 m³ per full load creates 7 + 7 + 6 m³. Leaving that quantity blank splits the order evenly to three decimals. Arrival times start from the required first arrival and use the same interval; review and adjust them for the actual jobsite logistics. No route travel time is inferred.

Alternatively add each load manually. Each row has quantity, planned departure and optional required arrival. Quantities must sum exactly to the complete order. Available truck count, slot identity, positive quantities, date order and Alberta time are validated. New concrete orders require the distribution in the form; other business units can optionally add it. Existing orders and older integrations remain compatible with their previous manual assignment flow; no historical plan is invented.

## Existing orders and assignment
Open the order and choose Set dispatch logistics / Edit dispatch logistics. Unstarted legacy assignments can be adopted using their existing IDs; fill in their proposed times. Assigned quantities cannot be changed or removed. Started trips retain their saved planned times. If the plan changes during editing, the save is rejected until the latest version is reviewed.

Use Plan delivery to select an unassigned planned trip, then driver and fleet vehicle. The trip's quantity and schedule are carried into that actual assignment. Each trip can be assigned once. The declared available-truck count bounds the distinct noncancelled vehicles allocated to this order; it can be adjusted before assigning more vehicles. One vehicle can cover multiple trips. This does not calculate route durations or solve fleet-wide scheduling conflicts; dispatcher coordination and the existing one-active-delivery checks still apply.

Changing a future, unstarted trip's schedule updates its assignment and records the plan revision in the order audit trail. Completed and cancelled orders cannot have their logistics rewritten. Aimsio reference changes retain the plan, chat, signatures and permanent order/load IDs.

## Daily operation
Drivers see planned departure and required arrival on their next delivery. The next ready load and GPS selection use planned departure order, even when assignments were created in a different order; an active trip always takes precedence. Planned times do not automatically mark production, departure, arrival, completion or customer acceptance.

Order logistics show planned versus actual departure with early/late/overdue minutes, plus actual arrival. The private customer tracking page shows planned departure and required arrival for assigned loads alongside actual events; internal logistics notes are not published. The current customer tracking endpoint and existing manual/GPS event sequence are unchanged.

## Persistence and authorization
Plan creation commits with the order and any inline customer/jobsite creation. Invalid plans roll the entire creation back. Manager-only plan writes use authenticated invoker wrappers, guarded private functions, explicit execution grants, row locks and optimistic version checks. Exact retries are idempotent; changed retry payloads are rejected. The existing orders/loads RLS and SELECT-only table grants remain in place. Revision snapshots are retained as logistics_updated activities. No inventory, maintenance or production consumption is generated by planning.

## Validation
Model and component tests cover distribution, rounding, invalid dates and sums, Alberta/DST handling, editor fields, assignment controls and planned-versus-actual display. Rollback SQL covers atomic order creation, retry integrity, roles, totals, duplicate slots/assignments, revision conflicts, preservation of started trips, legacy assignment adoption, audit history, private tracking and separation from real delivery events. Existing receipts, geofence and order-chat rollback tests pass. Security advisors show no additional findings. Physical phone testing remains a pilot check.

## Planned driver · 0.3.8
Each trip can select an active enrolled Mobile Concrete Fleet driver during order creation or editing. The server validates identity and records the canonical name. Plan delivery preselects and retains that driver; assigning the vehicle creates the actual delivery and its notification. To change an unassigned driver, edit logistics first. Assigned/started trips retain their delivery driver. Blank driver selections remain compatible with existing orders.
